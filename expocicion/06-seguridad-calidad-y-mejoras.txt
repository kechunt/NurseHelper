1. SEGURIDAD EN EL BACKEND
================================================================================

AUTENTICACIÓN
  - JWT (Bearer) generado en login; payload: userId, role.
  - Archivos: utils/jwt.ts, middleware/auth.middleware.ts
  - Variables: JWT_SECRET, JWT_EXPIRES_IN (default 24h)
  - Contraseñas: bcrypt en User entity (@BeforeInsert / @BeforeUpdate)

AUTORIZACIÓN (RBAC)
  - Roles: admin, nurse, supervisor, pharmacy (entities/User.ts)
  - middleware/role.middleware.ts: requireAdmin, requireAdminOrSupervisor,
    requireNurseOrAdminOrSupervisorOrPharmacy, restricciones por área, etc.
  - Routers sensibles: /api/shifts (admin/supervisor), /api/backup y /api/webhooks (admin)
  - reports-scope.helpers.ts: filtra datos de reportes según usuario

PROTECCIÓN HTTP
  - helmet: cabeceras de seguridad HTTP
  - cors: lista blanca (localhost, CORS_ORIGIN, *.vercel.app, ngrok en dev)
  - trust proxy: 1 (correcto detrás de Railway/Vercel)
  - Límite body JSON: 1 MB (anti payloads enormes)

RATE LIMITING
  - Global: rateLimitMiddleware en app.ts
  - Auth: authRateLimitMiddleware (login/register más estricto en producción)
  - Reports: 20 peticiones/minuto adicionales en router

VALIDACIÓN Y SANITIZACIÓN
  - DTOs con class-validator + validation.middleware.ts
  - sanitizeMiddleware: DOMPurify contra XSS en entradas
  - validateEnv(): obliga JWT_SECRET, DB_*, FIELD_ENCRYPTION_KEY en producción

DATOS SENSIBLES
  - field-encryption.util.ts: AES-GCM para campos médicos en BD
  - typeorm-encrypted.transformers.ts en entidades correspondientes
  - FIELD_ENCRYPTION_KEY obligatoria en producción (openssl rand -base64 32)

AUDITORÍA Y ERRORES
  - audit.service.ts: eventos de login
  - error-handler.ts: respuestas uniformes sin filtrar stack en producción
  - logger con niveles (LOG_LEVEL)

OPERACIONES PRIVILEGIADAS
  - Backup/restore: solo admin
  - Webhooks: solo admin
  - Cambio de rol de usuario: solo admin


2. SEGURIDAD EN EL FRONTEND
================================================================================

  - Guards en rutas: imposible abrir /admin sin rol admin (salvo manipular URL → API rechaza).
  - authInterceptor: adjunta token; logout automático en 401.
  - Timeout 15s y retry limitado en errores de red.
  - Token almacenado vía AuthService (no exponer en URLs).
  - Confirmación antes de borrados (ConfirmationService).
  - Registro público limitado a rol enfermería (política en backend).

Limitación conocida (exponer con honestidad):
  - La seguridad definitiva está en el servidor; el frontend solo oculta UI.


3. CALIDAD Y PRUEBAS
================================================================================

BACKEND (Jest)
  Ubicación: backend/src/__tests__/
  - unit/: controladores, servicios, middleware, jwt, sanitizer, cifrado, DTOs
  - integration/: estructura endpoints, pacientes API, full-system, notificaciones
  - migrations/: tests de migraciones
  Scripts: npm run test:unit, test:integration, test:coverage
  CI: MySQL 8.0 como service en GitHub Actions

FRONTEND
  - Unit: Karma + Jasmine (npm test en frontend)
  - E2E: Playwright (frontend/e2e/) — 9 archivos
    * Guards de rutas sin sesión
    * Smoke dashboards con API mockeada
    * Navegación por teclado en nurse main nav

CI/CD (.github/workflows/ci-cd.yml)
  Trigger: push y PR a main, develop
  Node: 20.x
  Secuencia: lint → build → tests en ambos paquetes
  E2E no depende de BD real (mocks HTTP)

LINT
  - ESLint en raíz, backend y frontend (eslint.config.cjs flat config)


4. BASE DE DATOS Y INTEGRIDAD
